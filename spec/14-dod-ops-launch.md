## §1 The Global DoD — Forty Checks

The build is complete only when `docs/dod-report.md` lists all forty checks PASS with evidence (command output or URL). The report is generated by `scripts/qa_gate.sh --dod` and committed; hand-ticked boxes do not count. Groups: **Deploy & health (G-01…G-06)**: `/health` 200 on API and MCP; `/health` `version` == deployed git tag's `VERSION`; PWA Lighthouse ≥ 90 (perf, a11y, best-practices); SEO sitemap covers 247 Jont pages + collections; preview envs expire ≤ 7 days; deploy workflow runs preview-first. **Data & platform (G-07…G-12)**: `db:verify OK (n checks)` on production D1; platform test suite green (VOL-05 §9); counter race test proves exactly-one-wins; KV write budget ≤ 200/day measured on a peak-shaped synthetic day; brake modes flip at 80%/95% in a staged test; error taxonomy audit — no response code outside VOL-05 §8. **Billing integrity (G-13…G-18)**: T6.1–T6.10 all green on production-shaped fixtures; Stars ladder renders 400/750/1500 from `/api/config`; USDT annual = ×10 exactly; webhook replay idempotence proven for both providers; downgrade keeps history (hidden-not-deleted verified); payout ledger cron posted one message with three totals. **Privacy & honesty (G-19…G-24)**: client-side Jonts transfer zero file bytes (mitm-captured on three Jonts); server-side Jonts label themselves in every surface; no payload bodies in any log; anonymous quota is halved exactly as stated; every quota meter shows real numbers + reset time; the checkout no-refunds sentence is in the same viewport as the pay button. **MCP & gateway (G-25…G-30)**: VOL-10 T10.1–T10.14 green; three gateway builds byte-identical on P0 verbs; `/.well-known/jontrix-mcp.json` live; gateway conformance suite in CI; AAT cannot manage tokens (negative test); revocation ≤ 60 s measured. **Catalog & DoD sweeps (G-31…G-36)**: J001–J050 live with per-Jont DoD reports; long-tail batches B1–B7 live or explicitly scheduled; registry equals seed (247 rows, 155/79/13); zero acceptance-row skips; zero budget busts (VOL-11 §7); `CORS Echo` + `cURL to Code` runnable from the extension on a foreign-origin tab. **Versioning & docs (G-37…G-40)**: version-hygiene grep passes (VOL-00 §0.7 — one literal in `src/version.ts` + `CHANGELOG.md` only); `CHANGELOG.md` ascending and complete; `docs/decisions.md` has an entry per AGENT CHOICE taken; runbooks exist and were each executed once in a drill (payout, incident, backup).

## §2 The Per-Jont DoD Format (every card, every tier)

A Jont ships when its card file (generated from the manifest, VOL-11 §6) ticks all ten: **(1)** manifest passes the zod schema; **(2)** harness green on every acceptance row (zero skips, fixtures committed); **(3)** pattern invariants hold (VOL-11 §4 — byte-stability, idempotence, spans, no-mutation as applicable); **(4)** performance budgets hold (VOL-11 §7); **(5)** PWA page renders with H1 = name and subtitle = problem statement verbatim; **(6)** execution-context label correct and true (C6); **(7)** tier gate works for anonymous, free, and paid (preview shows value before paywall); **(8)** MCP tool callable when `mcp_exposed` (schema-valid arguments, metered row in `jont_usage`); **(9)** SEO page live with canonical, JSON-LD, 3 FAQs; **(10)** card's DoD block committed with the harness log link. A Jont failing any item is not counted, not listed, not announced (VOL-00 §0.5).

## §3 CI and Deploy Workflows

**§3.1 `ci.yml`** (every push, PR): typecheck (strict, all workspaces) → lint (config presets) → unit tests → platform suite against Miniflare → Jont harness for changed `jonts/` → `db:verify` against a scratch D1 → **version-hygiene check** (VOL-00 §0.7) → seed-vs-registry equality → build all apps (API, MCP, PWA, extension, gateway×3 targets) → gateway conformance suite (npm build vs fixtures). Budget: the whole pipeline runs on GitHub Actions free (public repo) in < 15 min; no job may call a live third party (VOL-03 §6 exception applies only to deploy). **§3.2 `deploy.yml`** (push to `main`, manual gate for production): build → apply migrations to **preview** D1 → deploy preview → run smoke (`/health`, one client Jont, one server Jont, MCP handshake) → await the manual approval job → apply migrations to production → deploy production workers + Pages → verify `/health` version == tag → ping the dead-man switch → append the deploy line to `CHANGELOG.md` if the version advanced. **MUST:** production deploys are tagged (`V…` FRAZIYM version as the tag name); a failed smoke rolls back to the previous Workers version pin. **NEVER:** a production deploy from a red CI run, a migration applied to production before preview, or a manual `wrangler deploy` from a laptop (the workflow is the only road).

## §4 `scripts/qa_gate.sh` (the pre-flight the agent runs before every phase exit)

One gate, four stages, exit non-zero on any red: **(1) static** — the §3.1 pipeline re-run locally; **(2) data** — `db:verify` + seed equality; **(3) surface** — the phase's acceptance tables re-executed (VOL-01 §8, VOL-06 §8, VOL-07 §7, VOL-08 §5, VOL-09 §6, VOL-10 §10 as applicable); **(4) honesty** — the C8 sweep: no hard-coded prices (grep), no version literals outside `src/version.ts`, no invented claims in surface copy (diff against the card/registry text), no payload logging. `qa_gate.sh --dod` emits the §1 report skeleton. The gate is deliberately dumb and loud: it prints one PASS/FAIL line per check and stops at the first red, because an autonomous agent's worst habit is reading a red wall and shipping anyway.

## §5 Backup and Restore

D1: nightly export to R2 (`backup/d1/YYYY-MM-DD.sql.gz`, 30-day retention — a Cron Trigger running the built-in export; free-tier budget ≤ 31 Class-A ops/month, negligible). R2 `results`: versioning off (results are regenerable), but the bucket inventory is logged weekly. Secrets: no backup (they live in Workers; the runbook lists all seven with their rotation owner). Restore drill: once before launch, once per quarter — restore the latest export to a scratch database, run `db:verify` against it, record the drill in `docs/decisions.md`. **MUST:** a restore drill that has never run is a failed check (G-40), not a footnote. **NEVER:** a backup containing webhook secrets or user payload bodies (exports are schema + ledgers + entitlements; `results` bodies stay in R2 where they already live).

## §6 Operations — Cron Inventory, Watchdog, Maintenance Budget

The complete cron list (Workers Cron Triggers, all free, all inside the 100k req/day budget): **hourly** — sweep expired entitlements (VOL-06 §5), brake-level check (VOL-01 §6: read D1 usage totals, flip modes at 80%/95%), MCP device-code/idempotency purge (VOL-10 §6); **daily 00:05 UTC** — counter period rollover is implicit (period-keyed rows), invoice expiry (72 h), watchdog digest to the founder (one Telegram message: requests, signups, paid users, errors, brake state, version); **daily 03:00 UTC** — D1 backup (§5); **monthly 1st 00:10 UTC** — R2 results cleanup (expired `results`), payout summary (VOL-06 §7), AI-cache stats prune. **Dead-man switch:** a healthchecks.io check (free) pinged by the daily digest cron; a missed ping emails the founder — the under-10-minutes/week guarantee (C4) is this: every recurring duty is on this list, every failure path ends in exactly one message the founder reads, and nothing else pages anyone. The maintenance ledger (VOL-15 §6) logs every manual intervention with minutes spent; the quarterly review compares against the C4 budget.

## §7 Incident Runbook (contract)

`docs/runbooks/incident.md` defines three severities: **S1** (platform down, billing wrong, data exposed): flip brake to `read_only` (one KV write — the kill switch), post to `/api/status`, fix forward; **S2** (one surface or provider degraded): the FALLBACK ladder from the relevant volume applies (provider rotation VOL-05 §5, rails VOL-01 §5, gateway endpoints VOL-10 §4.9); **S3** (cosmetic): next scheduled release. Every incident appends to `usage_ledger` (`incident_open`, `incident_close`) with minute counts, and the post-mortem is three lines in the worklog-style format — no ceremony. **MUST:** the founder learns of S1 within one digest cycle; **NEVER** an incident fixed by a hand-edit to production data (data fixes are migrations or documented SQL run through the same deploy gate).

## §8 Launch Checklist & the 90-Day Roadmap

**Launch checklist (Phase-9 exit):** all forty G-checks PASS; domain DNS, registrar state, and the four routes verified; Stars + USDT test purchases flipped real entitlements; the extension store listing submitted (approval may lag — launch does not block on it, the PWA carries S3 in the meantime); the gateway published to npm + PyPI with binaries; SEO sitemap submitted to Search Console; the founder's payout runbook drill executed; a CHANGELOG line at `V01.00.000` — launch is, by definition, the first stable release (VOL-00 §0.7). **90-day roadmap (post-launch, the roadmap VOL-00 Phase 9 executes):** days 1–30 — long-tail batches B1–B2, watchdog tuning, first monthly payout cycle, SEO indexing review; days 31–60 — B3–B4, first AAT-driven usage review (which agent tools get called — feeds VOL-12/13 refinement), extension store listing live, Stars subscription retention review; days 61–90 — B5–B6 (or B7), the first FRAZIYM feature-release cadence (FF bumps per batch), pricing review against the never-undersell rule (VOL-01 §5.5), and the honest go/no-go on the two parked experiments: AdsGram (VOL-01 §5.4, ≥ 10k DAU) and Paddle fallback (real demand evidence required). Each roadmap item lands as a decision-ledger row when started, not as a memory.

## §9 Release Management (operates VOL-00 §0.7)

The release procedure is four commands and zero judgment: **(1)** `npm run release -- feature|bugfix|revision` bumps `src/version.ts` per the §0.7 bump rules (the script asserts the new string matches the FRAZIYM regex and that FF/BBB/RR arithmetic is legal — it refuses an illegal sequence like BBB bump with FF reset); **(2)** append the `CHANGELOG.md` line (version, UTC date, one summary sentence; the only file allowed to repeat the string); **(3)** commit `version bump → V…` + tag; **(4)** the deploy workflow publishes with that tag and G-38's grep proves hygiene. Derived package versions (npm/PyPI/extension semver mapping) are computed inside `deploy.yml` from the tag — never edited by hand. Stage transitions (beta → rc → stable) are founder-announced in the decision ledger with the passing evidence (the phase exit or DoD sweep that justifies it). **MUST:** every published artifact — `/health`, PWA about, extension about, gateway `--version`, CHANGELOG — reports the identical string; a mismatch is an S1 incident per §7.
