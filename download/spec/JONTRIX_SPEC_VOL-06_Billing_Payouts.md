## §1 Identity and Login (two providers, zero passwords)

Two login methods exist — Telegram and email OTP — and both produce the same artifact: a platform session per VOL-05 §3. **Telegram Login Widget** (browser): the PWA and extension embed the official widget bound to `@JONTRIX_bot`; the callback carries `id, first_name, username, photo_url, auth_date, hash`; the API recomputes the HMAC-SHA256 over the sorted key-value pairs with the bot token's SHA-256 as key, rejects anything older than 86400 s or with a bad hash, then upserts `users` + `identities(kind='telegram')` and issues the session. **Email OTP** (browser + bot fallback): the user submits an email; the API stores only `email_hash` (SHA-256) in `identities`, generates a 6-digit code, and delivers it via the bot when a Telegram identity is linked, else via the transactional-email provider chosen at build (AGENT CHOICE from `research/infra.md`'s free-tier email section; contract: ≥ 200 emails/day free, no card); the code is stored as its own salted hash with a 10-minute expiry, single use, max 5 verification attempts, max 3 sends/hour/email. **MUST:** both flows end in the identical session issuance and `usage_ledger` event (`login`, provider named); linking a second identity to an existing account is a merge of `identities` rows only — entitlements never fork per identity. **NEVER:** a password column anywhere, an OTP reusable or long-lived, an email stored in plaintext, or a login flow that bypasses the widget/OTP contracts above.

## §2 Account Lifecycle (contract)

Anonymous → (first login) → `users` row + `identities` row + `entitlements(tier='free')` → optional paid window (§5) → expiry → back to `free` with data retained per VOL-01 §4.4. Deletion: the PWA settings page offers "delete my account"; the API marks `users.status='suspended'`, revokes all tokens (VOL-10 cascade), deletes `identities`, `presets`, `results` (bodies + metadata) within 24 h via cron, keeps `jont_usage`/`usage_ledger` rows as pseudonymous aggregates (the usage ledger is billing evidence), and writes a `usage_ledger` `account_deleted` event. Suspension (abuse) is founder-only, via the same event with `actor='founder'`. **MUST:** the 60-second tier-flip rule (VOL-01 §4.4) and the 60-second entitlement-cache bump (`version` increment, VOL-04 §2) hold on every transition. **NEVER:** two `users` rows for one Telegram id, an entitlement row without a user, or deletion that quietly skips R2 bodies.

## §3 Stars Checkout (the Mini-App rail)

Flow (behavioral, binding): **(1)** the Mini App pricing page (VOL-08 §3) calls `POST /api/billing/stars/invoice {tier}` for a signed-in user with `source≠stars-active`; the API returns `{tier, stars, payload}` where `payload` is an opaque, HMAC-signed, 15-minute bundle naming user, tier, and price. **(2)** The Mini App opens Telegram's native payment via `Bot API openInvoice`; Telegram collects Stars. **(3)** The bot receives `pre_checkout_query` → the Worker validates the `payload` signature, price match against the seeded `plans` row, and answers `ok:true` within the 10-second window (answer late = sale lost; the handler does no D1 writes before answering). **(4)** `successful_payment` arrives → the Worker inserts `stars_purchases` (UNIQUE `telegram_payment_charge_id` = replay-proof) and grants the window per §5. **MUST:** prices come from `plans.price_stars` (400/750/1500 per VOL-01 §5.2) rendered via `/api/config`, never hard-coded; the receipt message (VOL-08 §4) fires within 60 s of step 4. **NEVER:** granting before `successful_payment`, a refund flow that touches Stars programmatically (Telegram admin-refunds only; the bot surfaces Telegram's own mechanics per VOL-01 §4.4), or an invoice payload valid beyond 15 minutes.

## §4 USDT Checkout (NOWPayments, the web rail)

Flow: **(1)** `POST /api/billing/usdt/invoice {tier, plan: 'monthly'|'annual'}` → the Worker calls NOWPayments `POST /v1/invoice` (fixed-price mode, `pay_currency` user-selectable among `usdttton`, price from `plans.price_usd_cents`, `order_id` = the platform `inv_` id) and stores the row per VOL-04 §2 with `status='new'`; the response hands the hosted `invoice_url` to the PWA. **(2)** The user pays on NOWPayments' hosted page (the platform never touches card rails or holds crypto). **(3)** NOWPayments POSTs the IPN to `POST /api/billing/usdt/ipn`; the Worker verifies the HMAC-SHA512 signature (sorted JSON, the IPN secret), checks `payment_status ∈ {finished, confirmed}`, matches `order_id` to an open invoice, and — only then — grants per §5 and sets `window_end_granted`. **(4)** The monthly cron marks stale `new/waiting` invoices `expired` after 72 h. **MUST:** IPN handling is idempotent through `webhook_events` UNIQUE `(provider, payload_hash)` (replays land as `duplicate` with no grant); the checkout page displays the no-refunds sentence in the same viewport as the pay button (VOL-01 §5.3, C8); renewal reminders fire at D-3/D-1/expiry+1 via bot and email with a one-tap invoice link. **NEVER:** granting on `sending`/`waiting` statuses, trusting an unverified webhook, or storing the NOWPayments API key anywhere but Workers Secrets (VOL-03 §2).

## §5 Entitlement Sync State Machine (the 60-second machine)

States: `free` · `paid` · `expiring` (paid, `window_end` within 3 days) · `expired-pending-sweep` (past `window_end`, awaiting the hourly cron). Transitions: `free→paid` on a verified grant (Stars step 4 or IPN step 3): set `tier`, `source`, `window_start=now`, `window_end = now + 31d (monthly Stars/USDT) | +366d (annual)`, bump `version`; if a different-source paid window is still open, the new grant **extends from the later of (current window_end, now)** — stacking is honest and stated in checkout copy. `paid→expiring` is derived at read time (no write). `expiring/expired→free` only via the hourly sweep cron: set `tier='free'`, keep `source='expired:{rail}'` for the downgrade narrative, bump `version`, append `usage_ledger` `downgrade`, trigger the D-3/D-1/expiry+1 reminders on the way. Grants are also exposed as an internal function for `grant`-source keys (founder comps, test fixtures) with the same writes. **MUST:** every transition appends `usage_ledger` and bumps `version` in the same transaction as the tier write; the sweep is idempotent (a second sweep of the same expired row is a no-op); renewal reminders deduplicate on `(user, tier, window_end, kind)`. **NEVER:** a tier write without a window, a window extension that shortens an existing end date, or any path that flips a tier without the ledger event.

## §6 Webhook Security Contract (all providers)

Every webhook route: (1) resolves the provider by path; (2) verifies authenticity per provider — Telegram: `secret_token` header match (set at webhook registration) + `pre_checkout`/`successful_payment` payload signature checks; NOWPayments: HMAC-SHA512 over the sorted JSON with the IPN secret; (3) computes `payload_hash` and inserts into `webhook_events` — a UNIQUE violation short-circuits to `duplicate` (200, no processing); (4) processes inside the envelope with a 25-second budget (webhook receivers must answer fast; slow work goes to the queue — Workers Queues free tier 10k ops/day per VOL-01 §6); (5) appends `usage_ledger` with the outcome. Source-IP allowlisting is applied for NOWPayments where their published ranges are current at build time, but the HMAC — not the IP list — is the trust anchor (ranges change; signatures do not). **NEVER:** a webhook route without all five steps, a 500 response to a duplicate (providers retry duplicates forever), or business logic (pricing, grants) computed from webhook payload fields without cross-checking the seeded `plans` row.

## §7 Payout Protocol (the C2 runbook — cash in hand, honestly)

This section is the founder-facing operating procedure the build agent documents in `docs/runbooks/payout.md` and arms with a monthly cron + Telegram reminder. **Stars rail:** Stars accumulate under Telegram's 21-day hold; on the monthly reminder the founder withdraws via Fragment to the self-custody TON wallet (GRAM), respecting the 1,000-Star (~$13) minimum — sub-minimum balances simply roll to next month; Fragment may prompt KYC once (passport/NID suffices per the E2 evidence; the runbook says so plainly). **USDT rail:** NOWPayments custody sweeps 0%-fee to the founder's USDT wallet (TRC20/TON) after each confirmed payment. **Conversion cadence (freeze-avoidance, not compliance theater):** convert in **one batch per month** — via Bybit or OKX P2P (0% fee, bKash/Nagad/Rocket listed, 122–124 BDT per USDT observed vs 119.9 official = the +2–3.5% FX bonus) — never as many small credits, because many small MFS credits are what trigger wallet freezes (the real Bangladesh risk, E2). Bookkeeping: the cron appends the month's rails totals to the payout ledger (VOL-15 §3) from `stars_purchases` + `invoices` and sends the founder one message with three numbers: Stars held / Stars withdrawable / USDT receivable. **MUST:** the runbook names FERA 1947's grey-zone status honestly and instructs one-batch conversions with saved P2P receipts; amounts above the founder's stated comfort line require the founder's own manual action — the platform automates bookkeeping, never the movement of founder money. **NEVER:** an automated P2P bot, a custodial exchange account owned by the platform, or a payout path touching a bank account (C2).
